What can custom coded actions do in HubSpot workflows?

Short answer

A custom coded action runs your own JavaScript inside a workflow, which lets it do four things no native action does: call an API, read the records associated to the enrolled one, do arithmetic between two properties, and aggregate many records into one message. It needs Data Hub Professional, now called Data Hub Professional. Each run is per enrolled record, inside a 20 second window, and any secret it uses is readable by anyone who can edit the workflow.

What a spec looks like

Every spec follows the same nine sections, so a team reads one and knows how to read all of them.

  • Outcome, when to use it and when not to
  • Prerequisites: properties, lists, tiers, with the JSON to create them
  • Enrollment and re-enrollment, then every step with its parameters
  • Known pitfalls, a test plan, variants, and the YAML build spec

What breaks, and how the specs prevent it

A workflow secret is readable by everyone who can edit the workflow

Storing an API key as a workflow secret keeps it out of the visible action configuration, but it does not hide it from your colleagues. Check in Settings who can view and edit workflow secrets, and keep that list as narrow as the credential deserves. Rotating a key on the vendor side breaks every future run, with no retry of the calls that already failed.

A 200 response is not proof the payload landed

An endpoint that returns 200 and then rejects the payload in its own response body shows up as a success unless the code reads the body too, not just the status. The same trap sits inside the CRM: a failed fetch that returns an empty list reads as a real zero. Every spec here outputs a distinct error code instead, so a failure shows as a failure in workflow history.

Rate limits pause the action and everything after it

A coded action runs per enrolled record, in 20 seconds, in 128 MB, and you set a rate limit per action. Hit that limit and the action pauses, along with every step that follows it. The CRM Search API called from inside the code is throttled separately, so a bulk import can starve a detection workflow that works fine at normal volume.

What this bundle builds

Eighty specs that all share one thing: a step where the native action list runs out and you write code instead. They come from the four jobs that keep hitting that wall. Turning free text into one standard value, because a lookup table of country spellings cannot live in a branch. Reading the records associated to the enrolled one, because a deal cannot see its own line items. Talking to something outside the portal, because there is no native action for your product API. And doing arithmetic, because a workflow branch compares two properties but never subtracts one from the other.

This suits an in-house operations owner who already has Data Hub and is not sure what it actually buys them, and an agency that keeps rewriting the same domain matching code on every portal. The five components map to the five shapes that code takes in a workflow: transformation and formatting, cross-object lookups and associations, external APIs and webhooks, scheduling and date math, then scoring and calculations. Every spec names its secrets, its input fields and its output fields before the first line of code.

How the pieces fit together

Start with the formatting specs. They need no token, no secret and no API call, so you can build one in twenty minutes and see the pattern: inputs in, lookup table, output fields, error branch. That build teaches you the shape of every other spec in the pack.

Cross-object work comes next, because it adds the first dependency: a private app token with read access on the objects you search. Company association from email domain is the one to build first, since duplicate detection, the line item check and the association caps all reuse its search and its free-mail exclusion list.

External calls come third, once you have somewhere safe to keep a secret and a convention for failure. Scheduling sits fourth: it reuses the earlier code but multiplies the execution count, which is where rate limits start to bite. Scoring comes last because a score is only as honest as the properties feeding it, and those properties are what the first three components clean up.

Buy this if your portal already has Data Hub Professional or Enterprise and the licence is underused, or if you build on client portals and keep rewriting the same normalization and matching code. You get value in the first hour from the formatting specs alone.

Questions admins ask

Do I need Data Hub Professional to use a custom code action?

Yes. The custom code action is gated to Data Hub Professional or Enterprise, now named Data Hub. Every spec in this pack uses one, so Starter and plain Professional portals of the other hubs cannot build them as written. Several specs carry a documented no-code alternative in their Variants section, and the native-only bundle collects 40 specs that need no code at all.

How many custom code executions do I get per month?

The specs in this pack disagree on this point and say so openly. The limits that are documented and that you can see yourself are the 20 second runtime, the 128 MB memory ceiling, and the rate limit you configure per action. Treat any monthly allowance figure as something to confirm against your own subscription before you schedule a daily sweep across the full database.

What happens when my code throws an error?

Nothing silently succeeds. Each spec catches the error and returns a result code plus a truncated error message as output fields, so the run shows as a failed execution in the workflow History tab. The branch that follows reads that code and routes to a task or an alert instead of treating a missing value as a clean result.

Can a workflow loop over several records and send one message?

Not with native actions. A standard workflow enrolls and acts per record, so fifty closed deals produce fifty notifications. The weekly digest spec does the aggregation inside the code: it queries the search endpoint for the date range, sums the amounts, formats one string and posts it once. At volume the query needs pagination, not a single unpaginated call.

Where do I put an API key that the code needs?

In a workflow secret, referenced from the code as an environment variable, never pasted into the code body. Every spec here that calls something external names its secrets in the header comment of its code file, so you know what to create before you build. A missing secret fails the action immediately rather than sending an unauthenticated request.
